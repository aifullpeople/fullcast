# contract.md rules

Detail for generating the third artifact of the `tasks` stage. Adapted from a template
contributed by the project owner — see `docs/architecture.md` §7 for why this exists
and how it connects to Gates (§8) and `context_project.md` (§11). This file has the
mechanics; that section has the rationale.

`contract.md` is a stack-agnostic, consumer-agnostic, behavior-only specification of
what the feature promises. Two readers use it — one producing the implementation
(`fullcast-developer`, treats it as an implementation checklist) and one verifying
it (`fullcast-evaluator`, treats it as the assertion contract). Neither role is named
inside the generated file; it only describes behavior.

## File identity

| Property | Value |
|---|---|
| Path | `.fullcast/<initiative-id>-<slug>/features/<feature-id>-<kebab-name>/tech-lead/contract.md`, sibling of `design.md`/`tasks.md` |
| Generated by | `fullcast-tech-lead`, same run as `design.md`/`tasks.md` |
| Source of truth | PRD content for this feature: Section 9 acceptance criteria (drives the Coverage Manifest), plus Capabilities, Experience, Error Handling (drive item generation). Sibling of `design.md`, not derived from its implementation choices. |
| Lifecycle | Read-only after generation. Regeneration is wholesale (re-run this stage). Reports go elsewhere (`../developer/*.md`, `../evaluator/summary.md`) — never into this file. |
| Hand editing | Not supported — the next regeneration overwrites it. |

If a PRD's acceptance-criteria or dependency-graph content isn't found under the
expected section number, locate it semantically instead (same principle the exemplogs'
`implement-feature` already used) — don't hard-fail just because a heading number
shifted.

## Document structure

```markdown
# Contract: <Feature Name>

*Generated by fullcast-tech-lead. Hand edits are overwritten on regeneration.*

## Prerequisites
<five fixed subsections, in order, empty ones omitted entirely:
 Runtime services, Persistent state, Static inputs, Configuration, External dependencies>

## Quality gates
<preamble: "Each gate must pass for the feature to be considered ready."
 then one bullet per applicable gate from architecture.md §8:
   - **<gate name>** — `<command>` — <what passing means>
 omit the whole section only if genuinely no gate applies>

## Coverage Manifest
<table: every in-scope PRD Section 9 AC for this feature -> covering item IDs>

## <Surface 1>
**Verification mode:** <one line>

### <Capability A>
**Common given:** <shared precondition, omitted entirely if none>

#### `<ITEM-ID-01>` — <short label>
- given: <precondition>
- when: <single atomic action>
- then:
  - <observable consequence>
- notes: <optional>

### <Capability B>
...

## <Surface 2>
...
```

Order: title, italic regeneration notice, Prerequisites, Quality gates (when present),
Coverage Manifest, then surfaces in catalog order (Service, HTTP API, CLI, UI, Worker,
Event, E2E). Capabilities in PRD order within a surface; items in increasing NN within
a capability. Never name "implementing agent" / "evaluating agent" inside the generated
file — that vocabulary belongs only to this rules file.

## Surface catalog

Top-level sections are evaluation surfaces, not architectural layers. Emit only what
this feature actually has.

| Surface | When it appears | Default `Verification mode` |
|---|---|---|
| `## Service` | Real consumer OUTSIDE this feature calls a programmatic interface defined here — see Service Admission Rule below | "Invoke the public function/method directly in-process; assert the returned value, thrown error, or persisted side-effect." |
| `## HTTP API` | Networked endpoints (REST/RPC/GraphQL) | "Send an HTTP request to the running service; assert response status, headers, body, and any direct persisted side-effect." |
| `## CLI` | Ships a command-line tool | "Spawn the binary with the given arguments and stdin; assert stdout, stderr, and exit code." |
| `## UI` | Human-facing surface | "Render the surface, drive it with user-like inputs; assert observable surface state and navigation." |
| `## Worker` | Async/background processing | "Enqueue or trigger the input; observe the side-effect after processing completes." |
| `## Event` | Publishes/subscribes to a bus | "Publish the event (or trigger its source); observe handlers, projections, downstream effects." |
| `## E2E` | A capability crosses surfaces and is only meaningful end-to-end | "Run the full system; drive it the way a real user would; assert cross-stack behavior." |

Open catalog — add a new surface (e.g. `## WebSocket`, `## MCP`) when a consumer would
genuinely exercise it differently from all existing ones; it must declare its own
`Verification mode`.

**Service Admission Rule:** `## Service` appears ONLY with a real consumer outside this
feature — a library/SDK's public API, a use case another feature names as a dependency
in PRD Section 8, a plugin host, an internal RPC service. Internal helpers, value
objects, entities, repositories, and use cases invoked only by this feature's own
handlers do NOT qualify — no `## Service` without a nameable external consumer.

**Anti-rule for items:** items describe observable behavior at the feature's OUTER
boundary. Never per-class/file/method/VO/entity/helper, never per-test-file/function —
that granularity belongs to `design.md`'s Testing Strategy, not here.

## Hierarchy

Two levels by default (`## Surface` → `### Capability` → `#### Item`). A third level
only for a genuinely large capability (≥ ~10 cohesive items). Sub-headers carry
**capability vocabulary** (behavioral intent: "Register", "Login"), never
surface-entity vocabulary (route paths, page paths) — the same capability name should
appear across `## HTTP API`, `## UI`, `## E2E` so items correlate by name. Entity
details (`POST /auth/register`) live inside each item's `when:`.

## Item schema

```yaml
- id: <SURFACE>-<CAPABILITY>-<NN>
  given: <declarative precondition>
  when: <single atomic action>
  then:
    - <observable consequence, technical or business, instructive language>
  notes: <optional one-line context>
```

| Field | Required | Content |
|---|---|---|
| `id` | yes | `<SURFACE>-<CAPABILITY>-<NN>`. Surface code: `SVC`, `API`, `CLI`, `UI`, `WRK`, `EVT`, `E2E`. Capability code: UPPERCASE hyphenated tokens from the capability label. `NN`: two-digit sequence within the capability. Feature ID is NOT part of this — the folder already disambiguates (contrast with `state.json` task IDs, which DO carry the feature id because tasks live in one flat list). |
| `given` | yes | Declarative precondition — state the consumer decides operationally how to reach. Never setup steps. |
| `when` | yes | Exactly one atomic action. |
| `then` | yes | List of expected observable consequences — see guard-rails below. |
| `notes` | optional | One line of interpretive context. Overuse signals the item should split. |

Render fields in this exact order (`id, given, when, then, notes`) so diffs stay
predictable.

**Guard-rails on `then`:**
1. **Surface cohesion** — every assertion must be verifiable through this section's
   `Verification mode`. A cross-surface check moves to `## Service` or `## E2E`.
2. **Action atomicity** — `when` is one action; `then` lists its direct, immediate
   observables. Delayed/async effects belong to `## Worker`/`## Event` items instead.
3. **Soft cap ~5 bullets, hard ~10** — above 5, flag for splitting; forces an
   "is this really one action?" check.
4. **Atomic bullet** — one observation per bullet. Structural grouping is fine
   (`body { id, email }`); conjoined observations are not (`status 201 and cookie set
   and row persisted` is three observations in one bullet).

**Common given:** when several items in a capability share a precondition, declare it
once under `### Capability`. Inheriting items write `given: (default)`; extending items
write `given: (default), and <extension>`; distinct items write their own full `given:`.

## Coverage Manifest

Second `##` section, directly under Prerequisites. Maps every **in-scope** PRD Section
9 AC to the item IDs covering it:

```markdown
| PRD Acceptance Criterion | Covered by |
|---|---|
| <verbatim AC text> | ITEM-ID-01, ITEM-ID-02 |
```

- First column: the AC's **verbatim text**, not a synthetic ID — the text is the stable
  identifier, so PRD wording drift shows up visibly on regeneration.
- An item may cover multiple ACs. An in-scope AC must have ≥ 1 covering item.
- Cross-feature integration ACs are NOT in this feature's manifest — they belong to the
  feature that owns them.
- **Out-of-scope ACs are dropped silently** — an AC whose verification falls outside
  this feature's `design.md` "Included" block (typically because a downstream feature
  in PRD Section 8 owns the verification) does not enter the manifest, generate items,
  or print a warning for the drop itself. Principle: every item here must be testable
  with this feature + its already-implemented Section 8 dependencies; nothing that
  needs a downstream feature to verify belongs in this contract.

**Hard coverage gate:** validate before saving (Step 7 of `design-and-tasks-rules.md`).
If any in-scope AC has zero covering items, **abort all three files** (no `design.md`,
no `tasks.md`, no `contract.md` — never a design whose contract was silently skipped):

```
ERROR: contract coverage gap for F<ID>. In-scope PRD Section 9 ACs with no covering item:
  - "<verbatim AC text>"
Either generate covering items, or revise the PRD/design if the AC no longer applies.
```

For inherently subjective ACs (visual identity, qualitative judgment), generate a
placeholder item with `notes: subjective; manual review only`, placed under the surface
matching the AC's vocabulary. When no surface fits, emit a `## Manual` section with
`Verification mode: Human review against the PRD; no automated assertion possible.`

## Prerequisites

First `##` section. Forward-looking conditions the contract assumes when items are
exercised — NOT yet met at generation time (the implementation doesn't exist yet);
producing them is part of the feature's deliverable, same as the code.

```markdown
## Prerequisites

These conditions describe the environment in which items in this contract are
exercised. Producing them is part of the feature's deliverable, alongside the
implementation itself — a contract whose prerequisites are not yet satisfied is not
failing, it is still being built. Once delivered, any missing condition halts item
execution until restored.

**Runtime services:**
- <each long-lived process or installed binary the contract assumes>

**Persistent state:**
- <each entity/account/row/message/token that must exist before items run — WHAT, not HOW>

**Static inputs:**
- `<path>` — <shape spec>. Used by: <item IDs>.

**Configuration:**
- <each env var, flag, or runtime setting items assume>

**External dependencies:**
- <network/sandbox/mock dependency items assume — omit subsection entirely if none>
```

Five fixed subsections, always this order, omitted entirely (no "none.") when nothing
applies.

| Subsection | Covers |
|---|---|
| Runtime services | Long-lived processes/binaries on PATH the items rely on |
| Persistent state | Entities/accounts/rows/sessions/tokens that must exist inside the system's store/queue/cache before items run — declared declaratively, never operationally |
| Static inputs | Files items reference by handle (fixtures, payloads) — path + shape spec + `Used by:` |
| Configuration | Env vars, runtime flags, settings items assume |
| External dependencies | Network access, sandboxes, mock servers items rely on |

`Persistent state` and `Static inputs` stay separate on purpose — they go through
different mechanisms (data-seeding vs. files on disk); conflating them makes the
implementer guess which one to use.

**Where the conventions come from — read `context_project.md`, don't rediscover:**
persistent-state seeding convention, fixture path convention, test-config convention,
and mock/external-dependency convention are exactly the kind of thing
`context_project.md` (architecture.md §11) exists to stop from being rediscovered every
feature. Check its "Discovered patterns" section first. If it's genuinely missing
(first feature, greenfield): in the interview, ask "where do fixtures live, how is test
data seeded, which env file does the test runner read" — then **append the answer to
`context_project.md`** so the next feature never asks again. Existing project
convention (or a prior feature's `contract.md`) is always authoritative over inventing
a new one; never split one feature across two conventions.

**Generation order for this section:** derive it LAST (after items exist to scan for
handles) but RENDER it FIRST in the file (above Coverage Manifest). Runtime services
come from `design.md`'s Architecture Impact/Component Overview; persistent state and
static inputs come from scanning every generated item's `given`/`when` for named
entities and files; configuration comes from `design.md`'s Technical Decisions; external
dependencies are emitted only when an item explicitly demands one.

**Relation to Common given:** Prerequisites bootstraps the ENVIRONMENT (once, before any
item runs); Common given prepares STATE per capability (re-applied per item via
`given:`). "Alice exists with password X" is a Prerequisite; "Alice is logged in for
this capability's items" is a Common given.

## Quality gates section — pulls from architecture.md §8, doesn't reinvent it

List only the gates from `.fullcast/config.yaml: gates` that are `true` AND
actually apply to this feature's surfaces (e.g., skip `dependency_boundary` if this
feature touches no package boundaries worth checking). For each gate's command: check
`context_project.md`'s "Gate commands" section first (cached from a prior feature) —
only discover and run the project's tooling directly if it isn't cached yet, then
append the discovered command there so the next feature's contract doesn't rediscover
it. Omit this whole section only if truly no gate applies (rare).

## Generation order (whole file)

1. Read PRD Section 9 ACs, Capabilities, Experience, Error Handling for the feature.
   PRD is the source of truth — ground the contract in PRD content, not in `design.md`'s
   implementation choices (consulting `design.md`'s Error Handling for edge-case
   discovery only is fine; letting its implementation choices shape items is not).
2. Filter Section 9 ACs against `design.md`'s "Included" scope — drop out-of-scope ACs
   silently (no manifest row, no item, no warning for the drop itself).
3. Determine applicable surfaces from PRD Capabilities/Experience/Provides signals; ask
   the user if ambiguous.
4. Identify capabilities (usually 1:1 with PRD capability bullets or grouped UX flows).
5. Per surface, per capability: generate items from the in-scope ACs + Error Handling,
   enriched with edge cases. Apply the four guard-rails. Every item must be testable
   with this feature + its already-implemented Section 8 dependencies.
   **If this feature persists anything to disk (file, embedded DB), generate at least
   one "fresh environment" item** — the mechanism's storage location (directory, file)
   does not exist yet, and the first write must still succeed. Do not assume the
   storage location pre-exists just because every other item's `given` can create it
   via `t.TempDir()` or an already-provisioned test environment — real deployments
   start from nothing. (Found the hard way: a Todo CRUD example shipped a JSON-file
   store whose Testing Strategy and Prerequisites never named this scenario; `go test`
   couldn't catch it because no test exercised it, and Evaluator couldn't catch it either
   because `contract.md` never had an item for it — the gap was in item generation,
   not in any Gate or in Evaluator's walk.)
6. Build the Coverage Manifest by matching generated items to in-scope ACs.
7. Build Prerequisites (rendered first, computed last) — see above.
8. Validate the hard coverage gate. Abort all three files together if it fails.

## Anti-patterns to refuse

- `then` that only restates `when`; items testing a single class/VO/entity in isolation.
- `given` with operational setup steps ("run `npx prisma migrate`...").
- `then` bullets saying "test passes" / "function is called" instead of an observation.
- Sections missing a `Verification mode:` line; manifest rows with empty "Covered by".
- Duplicate item IDs; surface-entity sub-headers (`### POST /auth/register`).
- `## Service` without a named external consumer.
- Items whose verification needs a feature listed downstream in PRD Section 8.
- Prerequisites written as a snapshot of current state instead of a forward-looking
  requirement.
- A handle used in an item (`given`/`when`) with no matching Prerequisites declaration,
  or a Prerequisites entry with no item citing it in `Used by:` (orphan declaration).
- Static-input paths invented instead of read from `context_project.md`'s convention.
- Persistent-state entries written operationally instead of declaratively; persistent
  state and static inputs conflated with each other.
- A feature that persists to disk with no "fresh environment" item anywhere in the
  contract (see Generation order step 5) — every `given` assuming the storage
  location already exists is exactly this anti-pattern in disguise.

## Worked example (excerpt)

```markdown
# Contract: Authentication System

*Generated by fullcast-tech-lead. Hand edits are overwritten on regeneration.*

## Prerequisites

**Runtime services:**
- the feature's backend service is running and reachable
- the persistence store is accessible, migrated, and starts in a known empty state

**Persistent state:**
- a user account `alice@example.com` / `Pass1234` exists, active. Used wherever items
  reference "alice".

**Configuration:**
- session cookie name is `session_token`; `TZ=UTC`

## Quality gates

Each gate must pass for the feature to be considered ready.
- **Compile** — `go build ./...` — the service builds cleanly.
- **Tests** — `go test ./...` — the automated suite passes.

## Coverage Manifest

| PRD Acceptance Criterion | Covered by |
|---|---|
| User can register with valid name, email, and password | API-REGISTER-01 |
| Login fails with a generic message on wrong credentials | API-LOGIN-02 |

## HTTP API

**Verification mode:** Send an HTTP request to the running service; assert response
status, headers, body, and any direct persisted side-effect.

### Register

**Common given:** no user exists with email "alice@example.com"; backend running with
default config.

#### `API-REGISTER-01` — happy path
- given: (default)
- when: POST /auth/register with body { name: "Alice", email: "alice@example.com", password: "Pass1234" }
- then:
  - 201 Created with body { user: { id, email: "alice@example.com" } }
  - the password is stored hashed, never plaintext

### Login

**Common given:** a user exists with email "alice@example.com" and password "Pass1234".

#### `API-LOGIN-02` — wrong password rejected
- given: (default), and the supplied password is "wrong"
- when: POST /auth/login with that password
- then:
  - 401 Unauthorized with code INVALID_CREDENTIALS
  - response message reads "Invalid email or password" (does not disclose which field)
```
